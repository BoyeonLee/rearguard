# PRD: RearGuard

> 카메라 영상 하나로 구현하는 자전거 후방 추월 사고 예방 엣지 AI

| 항목 | 내용 |
|---|---|
| 문서 버전 | v0.3 (PoC) |
| 타깃 | 도로를 주행하는 일반 자전거 라이더 |
| 구성 (PoC) | 노트북 Python(CPU 추론) + BLE 경고 유닛 2종(ESP32-C3) |
| 단계 | PoC: 녹화 영상·사진을 노트북에서 처리해 주간 도로 환경에서 핵심 기능 검증 |

> v0.3 변경: 개발 기준을 노트북 PoC로 변경(스마트폰은 최종 제품 구상으로 분리), 검출 모델 YOLO26n 확정, 1단계 경고 기준에 대형차 조건 추가, 성공지표별 측정 방법 명시

---

## 1. 제품 개요

자전거 시트포스트 높이의 후방 카메라 영상에서 뒤에서 오는 차량을 실시간으로 인식하고, **얼마나 가까이, 얼마나 빨리 지나갈지**를 예측합니다. 위험한 추월이 예상될 때만 단계적으로 경고하며, 뒤차 운전자에게는 후방 고휘도 LED로, 라이더에게는 핸들 LED와 경고음으로 알립니다.

**포지셔닝:** 레이더는 "뭔가 온다"를 알려주고, RearGuard는 "위험하게 온다"를 알려준다.

### 1.1 PoC 개발 기준

- 이 문서는 **PoC(개념 검증)** 를 목적으로 하며, 모든 개발은 **노트북 기준**으로 한다.
- 녹화 영상과 사진(nuScenes 후방 카메라, 자전거 높이에서 찍은 테스트 사진)을 노트북 Python에서 처리한다.
- 판단 결과는 BLE로 실제 ESP32-C3 경고 유닛(LED·부저)에 보내 물리적으로 출력한다.
- 실제 출시 계획은 없으므로 상업 라이선스, 제품 인증, 가격 정책은 고려하지 않는다.

### 1.2 최종 제품 구상 (개발 범위 밖)

PoC가 검증되었을 때 최종 제품이 어떤 모습일지에 대한 구상이며, 이 문서의 개발 대상이 아니다.

- 라이더가 이미 가진 스마트폰을 시트포스트에 후방으로 거치해 카메라 겸 연산 장치로 쓰는 앱 형태
- 폰·후방 LED 일체형 마운트, 처음 장착 시 폰 기울기 센서(IMU)로 카메라 각도 자동 측정 + 장착 높이 1회 입력
- 주행 중 각도 변화 감지 시 재보정 안내, 보조 장치임과 동작하지 않는 조건(야간·우천 등) 안내

## 2. 문제 정의

### 2.1 사용자 문제
자전거 라이더는 도로 가장자리를 주행할 때 뒤에서 오는 차량을 볼 수 없습니다. 후방 추돌과 근접 추월(close pass)은 라이더가 대응할 시간이 거의 없는 사고 유형이며, 대형차의 근접 추월은 풍압과 측면 접촉 위험이 특히 큽니다.

### 2.2 기존 해결책의 한계

| 기존 방식 | 한계 |
|---|---|
| 일반 백미러 | 라이더가 계속 시선을 돌려야 하고, 위험 여부는 스스로 판단해야 함 |
| 레이더 후방 감지기 | 거리와 접근 속도만 측정. 차량이 옆으로 얼마나 비켜 추월할지, 차종이 무엇인지 알 수 없어 차량이 많은 도로에서 경고가 과도함 → 경고 피로로 사용자가 경고를 무시함 |
| 녹화형 후방 카메라 | 사고 후 증거용이며 실시간 위험 판단 기능 없음 |
| 공통 | 전용 기기 구매 필요, 가격 부담 |

### 2.3 핵심 문제
> 라이더에게 필요한 것은 "뒤에 차가 있다"가 아니라 "이 차가 나에게 위험하게 지나간다"는 판단이다. 거리 기반 경고는 이 둘을 구분하지 못해 불필요한 경고가 많고, 그 결과 진짜 위험한 순간의 경고까지 무시된다.

### 2.4 해결 방향
- 카메라 영상으로 차량의 종류, 위치, 궤적을 인식해 **예측 측면 간격**과 **충돌까지 남은 시간(TTC)** 을 계산하고, 위험한 추월에만 경고한다.
- 모든 추론은 클라우드가 아닌 로컬 기기(PoC: 노트북)에서 수행해 통신 상태와 무관하게 낮고 일정한 지연시간을 보장한다.
- 카메라 위치는 대부분의 자전거에 있는 **시트포스트 높이(지면에서 약 60~80cm)** 를 기준으로 설계한다.

## 3. 사용자 시나리오

PoC에서는 아래 시나리오를 녹화 영상과 합성 궤적 데이터로 재현하고, 경고는 실제 ESP32-C3 경고 유닛으로 출력한다.

**시나리오 1. 처음 설정**
카메라 높이(줄자 실측)와 각도(삼각대 설정값)를 설정 파일에 입력한다. 카메라 렌즈 특성은 체커보드 사진으로 한 번 측정해 저장해 둔다.

**시나리오 2. 안전한 추월 (경고 억제)**
승용차가 충분히 비켜서 추월할 궤적으로 접근한다. 예측 측면 간격이 1.5m 이상이므로 핸들 유닛에 노란 LED만 표시되고 경고음은 울리지 않는다.

**시나리오 3. 대형차 근접 추월 (경고)**
트럭이 라이더 쪽으로 붙어서 접근해 예측 측면 간격이 2.0m 미만이 된다. 후방 LED가 고휘도 점멸로 바뀌어 트럭 운전자에게 라이더의 존재를 알리고, 핸들 유닛은 주황 LED와 짧은 비프음으로 라이더에게 알린다.

**시나리오 4. 충돌 경로 접근 (위험)**
뒤차가 감속 없이 라이더와 같은 선상으로 접근해 TTC가 2초 미만, 예측 측면 간격이 0.5m 미만이 된다. 후방 LED가 최대 밝기로 점멸하고, 핸들 유닛이 빨간 LED와 연속 경고음을 낸다.

## 4. 핵심 기능과 구현 기술

### 시스템 흐름

```
[노트북: Python, CPU]                                 [핸들 유닛]
 녹화 영상·사진 입력                                    ESP32-C3
 F4 카메라 설정 입력 (최초 1회)                          ├ RGB LED
 F1 차량 인식·추적                                     └ 부저
 F2 위험 추월 예측                                         ▲
 F3 위험도 판단 ──BLE(bleak)──┬────────────────────────┘
                              ▼
                [후방 유닛] ESP32-C3 + 고휘도 LED
```

### F1. 후방 차량 인식·추적
뒤에서 오는 차량을 검출하고 차종(승용차 / 대형차 / 이륜차)을 분류하며, 프레임이 바뀌어도 같은 차량으로 계속 추적한다.

| 구현 기술 | 내용 |
|---|---|
| 객체 검출 | YOLO26n (Ultralytics, COCO 사전학습 `yolo26n.pt`에서 파인튜닝). 선정 근거와 차선책은 `report/model_training_validation_design.md` 1장 |
| 모델 실행 | ONNX 또는 OpenVINO로 내보내 노트북 CPU에서 실행. 입력 크기 416 (640과 비교 실험 후 확정) |
| 데이터 | COCO 사전학습 가중치 + nuScenes 후방 카메라 데이터로 파인튜닝. 자전거 높이에서 찍은 사진은 **테스트 전용**(학습에 사용하지 않음). 상세는 `report/data_preprocessing_design.md` |
| 객체 추적 | 칼만 필터 + IoU 매칭 (ByteTrack 방식 경량 구현). 15 FPS를 못 맞추면 2프레임에 1번만 검출하고 사이 프레임은 칼만 예측값으로 채움 |

### F2. 위험 추월 예측
추적 중인 차량의 거리와 측면 위치를 추정하고, 1~3초 뒤의 궤적을 예측해 **추월 시 측면 간격**과 **TTC**를 계산한다.

| 구현 기술 | 내용 |
|---|---|
| 거리·측면 위치 추정 | 지면 평면 가정 + 호모그래피: 차량 bbox 하단(바퀴가 땅에 닿는 점)을 실제 도로 좌표로 변환. 렌즈 왜곡 보정은 이 점에만 적용 |
| 차폭 교차 검증 | 차종별 기준 차폭(승용차 1.8m / 대형차 2.5m / 이륜차 0.8m)으로 거리를 한 번 더 계산해, 호모그래피 결과와 30% 이상 다르면 신뢰도를 낮춤 |
| 측면 간격 기준 | 차량 중심이 아니라 **자전거에 가까운 쪽 차량 옆면** 기준 (\|옆 위치\| − 차폭의 절반) |
| 궤적 예측 | 칼만 필터 기반 등속·등가속 단기 외삽 |
| 위험 지표 | TTC, 최근접 통과 거리(CPA) |

**검증 데이터:** F2는 두 부분으로 나눠 검증한다.
- 거리·측면 위치 추정: 공개 데이터(nuScenes, 전처리 트랙 C)와 자전거 높이 테스트셋(트랙 E)
- 궤적 예측·TTC·CPA: 합성 궤적 데이터(트랙 D)와 nuScenes 연속 키프레임

### F3. 3단계 위험도 경고
위험 지표와 차종을 종합해 위험도를 판단하고, BLE로 후방 LED와 핸들 유닛에 전달한다.

| 단계 | 조건 (초기값, 실험으로 조정) | 핸들 유닛 | 후방 LED |
|---|---|---|---|
| 0 안전 | 접근 차량 없음 (정지·주차 차량, 멀어지는 차량 포함) | 꺼짐 | 기본 점등 |
| 1 주의 | 예측 측면 간격 ≥ 1.5m (대형차 ≥ 2.0m) | 노랑 LED | 기본 점등 |
| 2 경고 | 예측 측면 간격 < 1.5m (대형차 < 2.0m) | 주황 LED + 짧은 비프 | 고휘도 점멸 |
| 3 위험 | TTC < 2.0s 이고 예측 측면 간격 < 0.5m | 빨강 LED + 연속음 | 최대 밝기 점멸 |

| 구현 기술 | 내용 |
|---|---|
| 판단 로직 | TTC + CPA + 차종 가중치 규칙 기반 (판단 근거 설명 가능) |
| 경고 지속 | 히스테리시스 적용으로 단계가 짧은 시간에 오르내리며 깜빡이는 현상 방지. 단계 유지 시간 초기값 300ms, 실험으로 조정 |
| 통신 | BLE GATT, 위험도 단계 1바이트 전송 (노트북 Python `bleak` → ESP32-C3) |
| 하드웨어 | ESP32-C3 ×2, 고휘도 LED, RGB LED, 부저, Li-Po 배터리 |
| 눈부심 방지 | 후방 LED 밝기 상한과 점멸 주기 기준 설정 |
| 검증 | 합성 궤적 데이터(트랙 D)로 시나리오별 정답과 비교, 같은 데이터에 레이더 모사 규칙(트랙 D5)을 적용해 경고 수 비교 |

### F4. 카메라 장착 보정
시트포스트 높이는 라이더 체격에 따라 달라지므로, 카메라 높이와 각도를 입력받아 F2의 거리 추정 정확도를 유지한다. PoC에서는 센서 자동 측정 대신 실측값을 입력한다.

| 구현 기술 | 내용 |
|---|---|
| 카메라 내부 파라미터 | 체커보드 기반 카메라 캘리브레이션 (촬영 기기별 1회, OpenCV) |
| 카메라 각도 | 삼각대 설정값 입력 |
| 카메라 높이 | 줄자로 잰 높이 입력 |
| 높이 변경 대응 | 입력한 높이로 지면 좌표 변환을 다시 계산. 60·70·80cm 촬영 사진으로 검증 (트랙 E) |

### 공통 기술 스택

| 영역 | 선택 |
|---|---|
| 실행 환경 | 노트북 Python (NVIDIA GPU 없음, CPU 추론) |
| 영상 처리 | OpenCV |
| 학습 | PyTorch, Ultralytics, Google Colab 무료 GPU, 결과는 Google Drive에 저장 |
| 경고 유닛 연동 | Python `bleak` + ESP32-C3 |
| 평가 | Python. nuScenes 검증 장면, 합성 궤적 데이터, 자전거 높이 테스트셋(주차 차량 + 줄자 실측) |
| 테스트 촬영 | iPhone(촬영 도구로만 사용) + 삼각대 60·70·80cm |

## 5. 범위 & 비범위

### 5.1 범위 (PoC)
- F1~F4 핵심 기능 (노트북에서 녹화 영상·사진 처리)
- 주간, 비가 오지 않는 날씨(맑음·흐림)의 일반 도로
- 카메라 높이 약 60~80cm (시트포스트 높이)
- 노트북 → BLE → ESP32-C3 경고 유닛 물리 출력
- 레이더 방식 대비 오경보 감소 효과 검증

### 5.2 비범위

| 항목 | 이유 |
|---|---|
| 스마트폰 앱 개발, 실제 자전거 주행 장착 | PoC는 노트북 기준으로 검증. 최종 제품 구상(1.2)으로만 남김 |
| 야간·우천 | 별도 데이터와 저조도 대응 필요, PoC 이후 |
| 영상 녹화·저장, 클라우드 연동 | 핵심 가치와 무관, 개인정보 이슈 |
| 주행 기록, 지도, 통계 | 핵심 가치와 무관 |
| 보행자·자전거 등 비차량 객체 경고 | 후방 추월 위험의 주 원인 아님 |
| 딥러닝 궤적 예측, 단안 깊이 추정 네트워크 | CPU 실시간성 부담, 규칙 기반 검증 후 검토 |
| 전동킥보드·공유 PM | 거치 구조가 달라 향후 확장 |
| 출시 관련 (상업 라이선스, 제품 인증) | 출시 계획이 없는 PoC |

## 6. 성공지표

### 6.1 핵심 지표
> **레이더 방식 대비 불필요 경고 50% 이상 감소, 위험 추월 감지율 90% 이상 유지**

- 베이스라인: 같은 합성 궤적 데이터에 "거리와 접근 속도만 사용하는 경고 규칙"(레이더 모사 규칙, 전처리 트랙 D5)을 적용한 결과
- 불필요 경고: 정답이 0·1단계(안전)인 장면에서 2단계 이상 경고가 울린 경우
- 위험 추월 감지율: 정답이 2·3단계인 장면 중 2단계 이상으로 판단한 비율

### 6.2 기능별 지표 (PoC 목표)

| 기능 | 지표 | 목표 | 측정 방법 |
|---|---|---|---|
| F1 | 후방 30m 이내 차량 검출 재현율 | ≥ 95% | nuScenes 본 데이터 val 장면(20개 이상) |
| F2 | 측면 간격 추정 오차 (MAE, 0.5~2.5m 구간) | ≤ 0.3m | 자전거 높이 테스트셋 (트랙 E, 70cm) |
| F2 | TTC 추정 오차 | ≤ 0.5s | nuScenes 연속 키프레임(차량 ID 기준) + 합성 궤적 데이터 |
| F3 | 위험 추월(2·3단계) 감지 재현율 | ≥ 90% | 합성 궤적 데이터 (트랙 D) |
| F3 | 종단 간 지연 (프레임 입력 → LED 점등) | ≤ 200ms | 노트북 → BLE → ESP32 LED 점등까지 실측 |
| F4 | 장착 높이 변경 후 측면 간격 오차 증가 | ≤ 0.1m | 60·80cm 사진과 70cm 사진의 같은 위치 비교 (트랙 E) |
| 공통 | 처리 속도 (영상 입력 → 위험도 판단, 파이프라인 전체 출력) | ≥ 15 FPS | 노트북 CPU |
| 공통 | 30분 연속 동작 후 FPS 저하 (발열) | ≤ 20% | 노트북 CPU, 영상 반복 재생 |

## 7. 주요 리스크

| 리스크 | 대응 |
|---|---|
| 노트북 CPU 속도 부족 | ONNX/OpenVINO 변환, 입력 해상도 조정, 2프레임에 1번 검출 + 칼만 예측 |
| 학습 데이터와 제품의 시점 차이 (카메라 높이 약 1.57m vs 약 0.7m) | 시점 증강, 자전거 높이 테스트셋으로 실제 성능 확인 |
| 공개 데이터에 자전거 노면 진동이 없음 | 모션 블러·회전 증강, 추적 필터로 위치 흔들림 완화 |
| 단안 거리 추정 오차 (경사로, 굴곡로) | 차폭 교차 검증, 한계 조건 명시 |
| 근접 추월 데이터 수집의 위험성 | 실제 근접 추월은 촬영하지 않음. 위험 상황은 합성 궤적 데이터로 검증하고, 실측은 주차 차량 대상 정지 촬영 |

## 8. 기대 효과 (최종 제품 구상 기준)

**이미 보유한 스마트폰과 시트포스트를 그대로 활용해 추가 비용을 수만 원대로 낮추면서, 수십만 원대 레이더 제품이 못 하는 '위험한 추월만 골라내는 경고'로 라이더가 끄지 않는 안전 장치를 제공한다.** PoC는 이 중 '위험한 추월만 골라내는 경고'가 실제로 가능한지를 노트북에서 검증한다.
