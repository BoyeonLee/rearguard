| 항목 | 결정 |

| 차선책 | DEIMv2-N: 박스 위치 정확도가 목표에 못 미칠 때만 비교 (§1.4) |

| 학습 환경 | Google Colab 무료 GPU, 결과는 Google Drive에 저장 |

| 검출 모델 검증 1단계 | nuScenes val 장면: P·R·mAP50·mAP50-95 + **30m 이내 재현율**. 합격 판정은 본 데이터 val 장면 20개 이상 |
| 검출 모델 검증 2단계 | 자전거 높이 테스트셋(트랙 E): 거리 구간별 재현율, 박스 하단 오차 |
| 검출 모델 검증 3단계 | 노트북 CPU 속도: 파이프라인 전체 15 FPS 이상, 프레임→LED 200ms 이하 |
| 고려하지 않는 조건 | 상업 라이선스(출시 계획 없음), 모바일 기기 이전(노트북 PoC) (§1.5) |

> 참고: 모델 수치(AP, CPU 속도, 파라미터 수)는 각 모델의 공식 문서·논문 값이다(2026-10-08 조회, §1.6 출처). YOLO26의 세부 사양(레이어 번호, 옵티마이저 자동 선택 규칙 등)은 구현 전 §9의 확인 목록으로 설치된 버전에서 직접 확인한다.

## 1. 모델 선정

### 1.1 선정 조건

PoC 단계에서는 아래 네 가지 조건으로만 모델을 고른다.

| # | 조건 | 출처 | 모델 선택에 주는 의미 |
|---|---|---|---|
| ① | 노트북 CPU에서 파이프라인 전체 15 FPS 이상 (검출·추적·거리 계산·판단 포함), 프레임→LED 200ms 이하 | 조사 보고서 7장, PRD 6.2 | 검출만으로 시간을 다 쓰면 안 됨. 공식 CPU 측정값이 있는 모델이 유리 |
| ② | 30m 이내 차량 재현율 95% 이상 | PRD 6.2 | 먼 차량 = 작은 물체 검출 능력 |
| ③ | 박스 아래쪽 변으로 거리 계산 | 전처리 C1 | 박스 위치 정밀도(mAP50-95)가 거리 오차로 직결 |
| ④ | Colab 무료 환경에서 적은 데이터(nuScenes mini, 야간 제외 후 학습용 약 600장 추정)로 학습 | 조사 보고서 1장, 전처리 0장 | 적은 데이터 파인튜닝이 안정적이고, 세션이 끊겨도 이어서 학습 가능해야 함 |

**고려하지 않는 조건:** 상업 라이선스, 모바일 기기 이전. 이유는 §1.5에 적는다.

### 1.2 후보 비교

| 모델 | ① CPU 속도 | ② 작은 물체 | ③ 박스 정확도 (COCO AP50-95) | ④ 적은 데이터 학습 |
|---|---|---|---|---|
| **YOLO26n** | **공식 측정값 있음:** CPU ONNX 38.9ms (640, Intel Xeon 2.0GHz) | 작은 물체용 라벨 할당(STAL)·점진적 손실(ProgLoss)을 공식 기능으로 명시 | 40.9 (640) | 쉬움. 적은 데이터 파인튜닝 사례가 많고 중단 후 재개 기능 내장 |
| DEIMv2-N | CPU 측정값 없음 | 별도 언급 없음 | **43.0** (640). 박스를 단계적으로 다듬는 구조 | DETR 계열이라 데이터가 적으면 학습이 불안정할 수 있음 |
| D-FINE-N | CPU 측정값 없음 | 별도 언급 없음 | 42.8 (640). 위와 같은 구조 | 위와 같음 |
| YOLO11n | CPU ONNX 56.1ms (640). YOLO26n보다 느림 | | 39.5 (640) | 쉬움 |
| PP-PicoDet-S | **6.6ms** (416, 노트북 i7-10750H) | | 32.5 (416) | PaddlePaddle이라는 별도 학습 도구 필요 |
| YOLOX-Nano | 매우 가벼움 (0.91M 파라미터, 1.08 GFLOPs) | | 25.8 (416) | 공식 저장소 관리가 뜸함. 최신 PyTorch 호환 확인 필요 |
| RF-DETR-N | 30.5M 파라미터. 2.3ms는 GPU(T4) 기준이라 CPU에서는 무거움 | | 48.4 (384) | |

> AP는 입력 크기가 모델마다 달라(대부분 640) 대략적인 차이로만 본다. 같은 조건의 비교는 E0(§4)에서 직접 측정한다.

### 1.3 선정 이유

**YOLO26n을 PoC 모델로 선정한다.**

1. **① CPU 속도 근거가 있는 후보 중 가장 정확하다.** 640 입력에서 38.9ms(약 26 FPS)다. RearGuard가 쓰는 416 입력은 연산량이 약 40%로 줄어 20ms 안팎으로 추정되므로, 추적·거리 계산이 들어갈 여유가 있다. 이 값은 추정이므로 §7에서 노트북으로 실측한다.
2. **② 작은 물체 대응을 설계 목표로 명시한 유일한 후보다.** 30m 재현율 95% 목표와 바로 맞닿아 있다.
3. **④ 학습 위험이 가장 적다.** nuScenes mini는 학습용이 약 600장(야간 제외 후 추정)으로 적다. DETR 계열은 이런 조건에서 학습이 불안정할 수 있다. YOLO26n은 Colab에서 체크포인트로 끊긴 학습을 이어가는 기능까지 갖춰져 있다.
4. **NMS가 없어서** 차가 여러 대 보여도 처리 시간이 거의 늘지 않는다. 200ms 지연 목표에 유리하다.

### 1.4 차선책: DEIMv2-N

- **③ 박스 위치 정확도**만 보면 DEIMv2-N이 조금 더 유리할 수 있다(AP 43.0 vs 40.9). RearGuard는 박스 아래 변으로 거리를 계산하므로 의미 있는 차이다.
- 다만 **① CPU 속도 근거가 없고**, ④ 적은 데이터 학습 위험이 있어 기본 모델로 두지 않는다.
- **비교 시작 조건** (둘 중 하나라도 해당하면 실험 E9로 진행):
  - YOLO26n의 mAP50-95가 낮게 나와 §5.5 진단표의 "박스가 대충"에 해당할 때
  - 트랙 C의 거리 오차가 목표(측면 간격 MAE ≤ 0.3m)를 넘을 때
- 비교할 때는 먼저 노트북 CPU 속도(§7)부터 재고, 15 FPS를 못 넘으면 학습하지 않는다.

### 1.5 고려하지 않는 조건

| 조건 | 고려하지 않는 이유 |
|---|---|
| 상업 라이선스 | 출시 계획이 없는 PoC다(PRD 1.1). YOLO26n은 AGPL-3.0, 학습 데이터 nuScenes는 비상업(CC BY-NC-SA 4.0, 체크리스트 16번)이지만 비상업 PoC에는 문제없다 |
| 모바일 기기 이전 | PoC는 노트북 CPU 기준으로만 개발·검증한다(PRD 1.1). 스마트폰은 최종 제품 구상으로만 남긴다 |

## 2. 학습 데이터 구성

전처리 트랙 A(A1~A7)의 결과물을 YOLO 형식으로 저장해 사용한다.

### 2.1 데이터 규모 (예상)

| 구분 | 출처 | 규모 (예상) | 비고 |
|---|---|---|---|
| train | nuScenes mini, mini_train 중 야간 제외 5개 장면 × 후방 카메라 3대 | 약 600장 (추정) | 야간 장면 3개가 모두 mini_train에 있음 (체크리스트 2번) |
| val | nuScenes mini, mini_val 2개 장면 (scene-0103, 0916) × 3대 | 약 240장 | 장면이 2개뿐이라 점수가 흔들림 |
| 합격 판정 val (필수) | nuScenes 본 데이터 val 장면 20개 이상 × 후방 카메라 3대 | 수천 장 | 후방 카메라 사진만 골라 저장 (전처리 A1) |
| 확장 train (선택) | nuScenes 본 데이터 train 일부 (공식 분할 유지) | 수천~1만 장 | mini 결과가 부족할 때만 |
| test | 자전거 높이 사진 (트랙 E, iPhone 촬영) | 42장 (70cm 30장 + 60·80cm 12장) | **학습·조정에 절대 사용 안 함** |

> mini의 키프레임은 전체 404개이므로 후방 카메라 3대 × 404 = 약 1,200장이고, 야간 3개 장면을 빼면 약 850장이다. 장면별 키프레임 수가 조금씩 달라 train/val 장수는 실제로 세어서 기록한다.

**val이 2개 장면뿐이라는 문제:** 결과표 교재의 "Instances가 적으면 그 클래스 점수는 덜 믿을 만"에 해당한다. 특히 이륜차는 val에 몇 대 없을 수 있다. 그래서
- mini 단계의 val 점수는 "파이프라인이 제대로 도는지"와 "실험 간 상대 비교"용으로만 쓴다.
- 합격 판정은 본 데이터 val 장면(20개 장면 이상, 필수)으로 한다.

### 2.2 폴더와 data.yaml

```
rearguard/data/nusc_back/
├── images/train/  images/val/
├── labels/train/  labels/val/      ← 한 줄에 "클래스 x중심 y중심 너비 높이" (0~1 정규화)
├── train.txt                       ← 학습 이미지 경로 목록 (오버샘플링용, §2.3)
└── rearguard.yaml
```

```yaml
# rearguard.yaml
path: /content/drive/MyDrive/rearguard/data/nusc_back
train: train.txt
val: images/val
names:
  0: car          # 승용차
  1: large        # 대형차 (버스·트럭·트레일러·공사차량·구급차, 전처리 A3)
  2: two_wheeler  # 이륜차
```

### 2.3 클래스 불균형 (전처리 A8 연결)

- 학습 전에 클래스별 박스 수를 센다.
- 이륜차가 전체 박스의 5% 미만이면, `train.txt`에 이륜차가 들어 있는 이미지 경로를 2~3번 반복해 적는다(오버샘플링). 이 방법은 학습 코드를 고치지 않아도 된다.
- 교재 6장의 `cls_pw`(클래스 가중치)는 설치된 버전에서 지원 여부를 확인한 뒤 보조 수단으로만 쓴다. 두 방법을 동시에 쓰지 않는다(효과가 겹쳐서 원인 구분이 안 됨).

### 2.4 걸러낸 박스 처리 (전처리 A5 연결)

- YOLO 학습 도구에는 "무시 영역" 기능이 없다(확인 필요). 따라서 전처리 보고서의 **대안 2(필터링 유무 비교)** 를 실험 E5로 진행한다.
- 추가 대안: 걸러낸 박스 영역을 회색(114)으로 칠해서 "차가 있는데 차 아님으로 배우는" 문제를 없앤다. E5에서 함께 비교한다.

## 3. 학습 설정

### 3.1 설정값과 근거

| 인자 | 값 | 근거 (교재 장 / 기존 문서) |
|---|---|---|
| `model` | `yolo26n.pt` | 작은 데이터·CPU 추론. n으로 시작해 정체될 때만 s 검토 (교재 1장) |
| `imgsz` | 416 | 전처리 A7·B4와 일치. 640과 비교 실험 (E3) |
| `freeze` | 10 | 소규모 + 유사 도메인의 표준 선택. 레이어 0~9(백본 대부분)는 고정하고, 레이어 10부터 넥·헤드까지 학습 (교재 5장) |
| `epochs` | 150 | 파인튜닝은 빨리 수렴. 조기 종료가 실제 종료 시점을 정함 |
| `patience` | 20 | 기본값 100은 파인튜닝에 너무 큼 (교재 4장) |
| `batch` | -1 | Colab에 배정되는 GPU가 매번 다르므로 VRAM에 맞춰 자동 산정 (교재 2장) |
| `optimizer` | `auto` | 총 반복 1만 회 미만이면 AdamW 자동 선택. **`lr0`를 직접 바꾸는 실험에서는 반드시 명시** (교재 4장 함정) |
| `warmup_epochs` | 3 (기본값) | 사전학습 가중치를 첫 배치부터 흐트러뜨리지 않도록 유지 (교재 4장) |
| `amp` | True (기본값) | 끄면 느려지고 정확도 이득 없음 (교재 2장) |
| `cache` | True (RAM) | mini 규모는 RAM에 충분히 올라감. 첫 에폭만 느림 (교재 2장) |
| `mosaic` | 0.5 | 소형 데이터에서 온전한 원본을 볼 기회 확보 (교재 6장) |
| `close_mosaic` | 10 (기본값) | 마지막 10에폭은 모자이크 없이 실제 모습으로 마무리 |
| `multi_scale` | False | 실행 해상도가 하나(416)뿐이므로 불필요 (교재 3장) |
| `seed` | 0 | 실험 간 비교를 위해 고정 |
| `save_period` | 10 | Colab 세션이 끊겨도 10에폭 단위로 복구 |

### 3.2 증강: 전처리 설계(A8) → YOLO 인자 대응

| 전처리 A8 항목 | YOLO 인자 | 값 | 비고 |
|---|---|---|---|
| 좌우 반전 50% | `fliplr` | 0.5 | 좌측·우측 통행 데이터 모두 학습 |
| 확대·축소 ±20% | `scale` | 0.2 | 기본값 0.5와 비교 가능 (E3과 별개로) |
| 상하 이동 ±10% | `translate` | 0.1 | |
| 약한 원근 변형 | `perspective` | 0.0001~0.001 | **단위가 Albumentations와 다름.** 몇 장 그려서 눈으로 확인 후 결정 |
| 소폭 회전 ±5° | `degrees` | 5 | |
| 밝기 ±25% | `hsv_v` | 0.25 | 대비·감마는 직접 대응 인자 없음 |
| 모션 블러, JPEG 노이즈, 그림자 | (내장 인자 없음) | | 아래 참고 |

- 모션 블러·JPEG 노이즈·그림자 합성은 내장 인자가 없다. 두 가지 방법 중 하나를 쓴다.
  1. **오프라인 증강:** 장면 분할(A6)이 끝난 뒤 **train 폴더 사진에만** Albumentations로 변형본을 만들어 추가한다. val·test에는 절대 넣지 않는다.
  2. 학습 코드의 데이터 변환을 직접 확장한다 (난도가 높아 PoC에서는 1번 권장).
- 학습 시작 전 `train_batch*.jpg`(학습 도구가 자동 저장하는 증강 미리보기)를 열어, 차가 찌그러지거나 박스가 어긋나지 않았는지 눈으로 확인한다.

## 4. 실험 계획

**원칙: 한 번에 한 가지만 바꾼다.** 두 개를 동시에 바꾸면 무엇 때문에 좋아졌는지 알 수 없다. 기준(E2)에서 하나씩만 바꾼다.

|---|---|---|---|---|
| E0 | 사전학습 모델 그대로 | 학습 없음. COCO의 car / bus+truck / motorcycle을 3클래스로 묶어 평가 | 파인튜닝 효과를 재기 위한 **기준점** (전처리 8장 2번) | 가장 먼저 |
| E1 | 파일럿 | `fraction=0.1`, 3에폭 | 경로·라벨·저장이 끝까지 정상 동작하는지 | E0 직후 |

## 5. 검출 모델 검증 1단계: nuScenes val (검출 성능)

### 5.1 결과표 읽는 법 (RearGuard 기준)

학습이 끝나면 아래 형식의 표가 나온다(수치는 예시).

```
Class     Images  Instances  Box(P     R      mAP50  mAP50-95)
all          240        900  0.84   0.78    0.80     0.57
car          238        700  0.88   0.83    0.86     0.63
large        120        160  0.80   0.75    0.78     0.55
two_wheeler   30         40  0.70   0.60    0.62     0.40
```

| 항목 | 뜻 | RearGuard에서의 의미 |
|---|---|---|
| Instances | 정답 박스 개수 | 이륜차처럼 수십 개뿐이면 그 줄은 참고만 한다 |
| P (정밀도) | 찾았다고 한 것 중 맞은 비율 | 낮으면 헛경보의 원인. 단, 추적 단계에서 일부 걸러짐 |
| R (재현율) | 실제 차 중 찾아낸 비율 | **놓친 차는 경고를 못 한다.** 안전 장치에서 가장 중요 |
| mAP50 | 박스가 대충 맞으면 정답(IoU 0.5) 기준의 종합 점수 | **모델 선택의 주 지표** |
| mAP50-95 | 박스가 얼마나 딱 맞는지까지 본 점수 | **거리 추정 정확도와 직결.** 박스 아래 변이 어긋나면 거리가 틀어짐 |

**RearGuard에서 mAP50-95를 함께 보는 이유:** 일반 검출 과제에서 "mAP50 높음 · mAP50-95 낮음"은 "찾긴 찾는데 박스가 대충"이라는 정도의 진단이다. 하지만 RearGuard는 박스 **아래쪽 변**을 땅에 닿는 점으로 써서 거리를 계산하므로(전처리 C1), 박스가 대충이면 거리가 대충이 된다. 자전거 높이(약 0.7m) 카메라에서는 아래 변이 몇 픽셀만 어긋나도 먼 차의 거리가 수 미터씩 변한다.

### 5.2 평가 실행

```python
m = YOLO(f"{RUNS}/e2_n416_f10/weights/best.pt")
m.val(data="rearguard.yaml", imgsz=416, conf=0.001, split="val", plots=True)
```

- 검증 때는 `conf=0.001`로 곡선 전체를 그려야 mAP가 제대로 계산된다. 0.25는 추론(predict) 기본값이다(결과표 교재 5장).
- `plots=True`로 저장되는 PR 곡선, 혼동 행렬(confusion matrix)을 함께 본다. 혼동 행렬에서 **대형차 ↔ 승용차**, **이륜차 ↔ 배경** 혼동이 많은지 확인한다.

### 5.3 RearGuard 전용 지표 (직접 계산)

학습 도구의 결과표는 거리와 무관하게 모든 박스를 같이 센다. PRD 목표는 "30m 이내"이므로 별도 스크립트로 계산한다.

| 지표 | 계산 방법 | 목표 |
|---|---|---|
| **30m 이내 재현율** | nuScenes 3D 정답에서 카메라까지 거리를 구해 30m 이내 정답만 남기고, 운영 conf에서 IoU ≥ 0.5로 매칭된 비율 | ≥ 95% (PRD F1) |
| 거리 구간별 재현율 | 0~10 / 10~20 / 20~30 / 30~50m 구간별로 위 계산 | 구간별 하락 지점 파악 |
| 클래스별 30m 재현율 | 위를 클래스별로 | 이륜차가 목표 미달인지 확인 |
| 박스 하단 오차 | 매칭된 박스 쌍의 아래 변 y좌표 차이(원본 픽셀) | 트랙 C 거리 오차 분석에 넘김 |

- 거리 기준점은 전처리 C6과 같게 **차량 앞면 바닥**으로 맞춘다.
- 정답은 A5 필터(가시성 40% 미만, 라이다 점 0개 등)를 거친 박스만 쓴다. 학습 때와 다른 기준으로 채점하면 점수가 왜곡된다.

### 5.4 운영 conf 임계값 정하기

검증용 conf(0.001)와 실제 사용할 conf는 다르다. 결과표 교재 4장처럼 conf를 올리면 정밀도↑ 재현율↓, 내리면 반대다.

1. val에서 conf를 0.05 ~ 0.50까지 0.05 간격으로 바꾸며 **30m 이내 재현율**과 정밀도를 계산한다.
2. **30m 재현율 95% 이상을 만족하는 conf 중 가장 높은 값**을 운영 conf로 정한다. 안전 장치이므로 재현율을 먼저 맞추고, 남는 여유로 정밀도를 올린다.
3. 낮은 conf 때문에 생기는 헛검출은 추적 단계에서 "연속 N프레임 이상 검출된 차만 인정"하는 규칙으로 줄인다(F1 추적). 이 N은 F2·F3 검증에서 정한다.

### 5.5 결과표 진단표 (결과표 교재 7장 → RearGuard 처방)

| 증상 | 해석 | RearGuard 처방 |
|---|---|---|
| P 높음 · R 낮음 | 확실한 것만 찾고 많이 놓침 | 운영 conf 낮추기 → 거리 구간별 재현율로 어디서 놓치는지 확인 → 먼 차라면 E3(640) |
| P 낮음 · R 높음 | 헛검출 많음 | 혼동 행렬 확인. 간판·건물 오검출이면 배경 사진 추가, 추적 단계 N프레임 규칙 |
| mAP50 높음 · 50-95 낮음 | 박스가 대충 | **거리 오차 위험.** 3D→2D 변환(A4) 클리핑 확인, 라벨 품질 점검 → 그래도 낮으면 E9(DEIMv2-N) |
| 전부 낮음 | 덜 배움 또는 데이터 문제 | §3.4 점검 항목부터 (라벨 0개, 클래스 번호, 경로) |
| 이륜차만 낮음 | 데이터 부족 또는 자전거와 혼동 | 오버샘플링(§2.3) → E6 |
| E0보다 파인튜닝이 낮음 | 사전학습 지식 훼손 | 학습률·`freeze` 확인, `optimizer` 명시 여부 확인 |

## 6. 검출 모델 검증 2단계: 자전거 높이 테스트셋 (트랙 E)

nuScenes 카메라는 약 1.57m 높이(체크리스트 14번), 자전거 높이 카메라는 약 0.6~0.8m(기본 0.7m)다. 1단계 점수가 좋아도 이 차이 때문에 실제 성능은 다를 수 있다. 2단계는 **"교재에서 잘하던 학생이 실전 시험에서도 잘하는가"** 를 본다.

### 6.1 절차

1. 트랙 E 기본 세트 30장(70cm, 거리 5~30m × 옆 간격 0.5~2.5m)을 **학습과 완전히 같은 전처리**(B3~B5)로 넣는다.
2. 운영 conf(§5.4)로 추론하고, 직접 그린 2D 정답 박스와 IoU ≥ 0.5로 매칭한다.
3. 아래 표를 채운다.

| 지표 | 계산 | 목표 |
|---|---|---|
| 거리 구간별 재현율 | 0~10 / 10~20 / 20~30m (§5.3과 같은 구간. 5·10m / 15·20m / 25·30m 사진) | 30m까지 놓치는 차 없음 |
| 박스 하단 오차 | 정답 박스와 예측 박스의 아래 변 차이(픽셀) | 트랙 C의 거리 오차 계산에 사용 |
| 박스 하단 → 거리 오차 | 트랙 C를 거친 추정 거리 − 줄자 실측 거리 | PRD F2 목표(측면 간격 MAE ≤ 0.3m)와 연결 |
| 높이 변경 세트 (60·80cm 12장) | 같은 위치의 70cm 사진과 재현율·박스 하단 오차 비교 | 트랙 C의 F4 평가(측면 간격 오차 증가 ≤ 0.1m)로 넘김 |

### 6.2 1단계와 비교해서 판단하기

| 결과 | 해석 | 다음 행동 |
|---|---|---|
| 1단계 ≈ 2단계 | 시점 차이 영향 작음 | 다음 단계(F2·F3)로 진행 |
| 1단계 ≫ 2단계 | 시점 차이(도메인 격차)가 큼 | 증강 강화(`scale`, `perspective`) → E8(2단계 파인튜닝) 검토 → 자전거 높이 학습 데이터 소량 확보 검토 |
| 2단계에서 가까운 차(5m)만 실패 | 차가 화면 밖으로 잘리거나 너무 큼 | 학습 데이터의 잘린 박스 처리(A4 클리핑) 확인 |

### 6.3 주의

- 30장은 통계적으로 매우 작다. 재현율 1장 차이가 약 3%p다. 점수 자체보다 **어떤 조건에서 실패하는지**를 사진으로 확인하는 데 쓴다.
- 이 결과를 보고 설정을 고쳤다면, 그 테스트셋은 이미 "본 시험지"가 된다. 설정을 고친 뒤 최종 확인은 **새로 찍은 사진**으로 한다.

```python
fast = YOLO("best.onnx")
for _ in range(10): fast.predict("frame.jpg", imgsz=416, verbose=False)   # 예열
t = time.perf_counter()
for _ in range(200): fast.predict("frame.jpg", imgsz=416, verbose=False)
print("FPS:", 200 / (time.perf_counter() - t))
```

### 7.2 측정 항목

| 항목 | 측정 방법 | 목표 (PRD·조사 보고서) |
|---|---|---|
| 검출 FPS (검출 단독) | 위 코드, 416 / 640 각각 | 참고값. 파이프라인 여유를 보기 위해 기록 |
| 파이프라인 FPS | 영상 입력 → 검출 → 추적 → 거리 → 위험도 판단까지 전체 | ≥ 15 FPS (PRD 6.2) |
| 형식별 비교 | PyTorch / ONNX / OpenVINO | 가장 빠른 형식 채택 |
| 종단 간 지연 | 프레임 읽기 → 검출 → 추적 → 판단 → BLE → ESP32 LED 점등 | ≤ 200ms |
| 30분 연속 동작 | 영상 반복 재생하며 FPS 기록 | 저하 ≤ 20% |
| 내보내기 후 정확도 | ONNX 모델로 §5.2 val 재실행 | PyTorch 대비 mAP50 하락 0.01 이하 |

- 15 FPS를 못 맞추면 순서대로: ① OpenVINO로 바꾸기 ② 2프레임에 1번 검출 + 사이 프레임은 칼만 필터 예측(전처리 B6) ③ 입력 크기 축소(320). 모델을 바꾸는 것은 마지막이다.
- E3(640)은 재현율이 좋아져도 이 표의 파이프라인 FPS가 15를 못 넘으면 채택하지 않는다.

## 11. 초보자를 위한 핵심 정리

- **작은 모델부터.** 데이터가 적을 때 큰 모델은 문제를 푸는 대신 답을 외운다. n으로 시작하고, 크기를 올려도 안 좋아지면 문제는 모델이 아니라 데이터다.
- **처음부터 배우지 않는다.** COCO로 이미 "차가 무엇인지" 배운 모델에서 시작하면, 우리는 "뒤에서 본 차"만 추가로 가르치면 된다.
- **학습 전에 리허설.** 라벨 경로가 틀리면 에러 없이 조용히 엉터리 학습이 끝난다. val 한 번, 10% 파일럿 한 번이 몇 시간을 아낀다.
- **점수표의 숫자보다 제품 목표.** mAP가 높아도 30m 안의 차를 놓치거나, 노트북에서 느리거나, 자전거 높이에서 못 찾으면 불합격이다.
- **RearGuard는 박스의 "아래 변"이 중요하다.** 거리를 박스 아래 변으로 계산하므로, "대충 맞는 박스"(mAP50)만이 아니라 "딱 맞는 박스"(mAP50-95)도 챙긴다.
- **한 번에 하나만 바꾼다.** 두 개를 같이 바꾸면 무엇이 효과였는지 알 수 없다.
- **시험지는 미리 보지 않는다.** 자전거 높이 테스트셋은 학습에도, 설정 조정에도 쓰지 않는다. 쓰게 되면 새 사진으로 다시 시험한다.
