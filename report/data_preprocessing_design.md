## 0. 결정 사항 요약

| 항목 | 결정 |
|---|---|
| 개발 환경 | 노트북 Python (CPU 추론), 학습은 Google Colab 무료 |
| 검출 모델 | YOLO26n (선정 근거는 모델 설계 보고서 1장) |
| 학습 데이터 | nuScenes만 사용. mini로 시작 → 필요 시 본 데이터 train 일부로 확장 (선택) |
| 합격 판정 데이터 | nuScenes 본 데이터 val 장면 20개 이상 (**필수**). mini val은 2개 장면뿐이라 점수가 흔들림 |
| 직접 촬영 | iPhone(촬영 도구로만 사용)으로 자전거 높이(60·70·80cm) 사진 42장, **테스트 전용** (학습에 사용하지 않음) |
| 판단 로직 검증 | Python 합성 궤적 데이터 + 레이더 모사 규칙 비교 |
| CARLA | 보류 (GPU 확보 시 추가) |
| 검출 클래스 | 승용차 / 대형차 / 이륜차 |

> 참고: nuScenes의 세부 사양(카테고리 이름, 라벨 주기, 비식별화 여부, 제공 스크립트 등)은 `nuScenes_checklist.md`로 공식 자료와 실제 데이터에 대조해 확인 완료했다(2026-10-07).

## 1. 전처리 전체 구조

RearGuard의 전처리는 쓰임에 따라 다섯 갈래(트랙)로 나뉜다.

```
[트랙 A] 학습 데이터 준비 (오프라인, 1회)
 nuScenes → A1 장면 선별 → A2 키프레임 추출 → A3 클래스 통합 → A4 3D→2D 박스 변환
          → A5 박스 필터링 → A6 장면 단위 분할 → A7 리사이즈·레터박스 → A8 데이터 증강(학습 시)
          → 검출 모델 학습 (F1)

[트랙 B] 실시간 추론 전처리 (매 프레임)
 영상 프레임 → B1 시간 기록 → B2 품질 검사 → B3 관심 영역 처리 → B4 리사이즈·레터박스
            → B5 색상·정규화 → 검출 모델 → 추적

[트랙 C] 거리 추정 기하 전처리 (매 프레임, 검출 결과에 적용)
 검출 박스 → C0.5 레터박스 좌표 되돌리기 → C1 접지점 추출 → C2 접지점 왜곡 보정 → C3 지면 좌표 변환
          → C4 차폭 보정 → C5 이상치 제거 → 추적 필터 → TTC·측면 간격 (F2 거리·측면 위치)

[트랙 D] 판단 로직 검증용 합성 궤적 데이터 (오프라인)
 D1 시나리오 정의 → D2 정답 생성 → D3 측정 오차 주입 → D4 균형 조정
          → 판단 로직 검증 (F2 궤적 예측·TTC·CPA, F3) → D5 레이더 모사 규칙과 비교

[트랙 E] 자전거 높이 테스트셋 (오프라인, 1회)
 E1 촬영 → E2 정답 기록 → E3 비식별화 → E4 라벨링 → (트랙 B·C와 동일 전처리 후 평가)
```

**쉽게 말하면:** 트랙 A는 "AI를 가르칠 교재 만들기", 트랙 B는 "실전에서 AI에게 보여줄 화면 다듬기", 트랙 C는 "AI가 찾은 차의 진짜 거리 계산하기", 트랙 D는 "판단 능력을 시험할 문제지 만들기", 트랙 E는 "최종 시험지 만들기"다.

## 2. 트랙 A: 학습 데이터 준비

### A1. 장면 선별
| 항목 | 설정 |
|---|---|
| 시작 데이터 | nuScenes mini (10개 장면): 파이프라인 검증, 실험 간 비교용 |
| 합격 판정 데이터 (필수) | nuScenes 본 데이터 val 장면 20개 이상 |
| 학습 확장 (선택) | mini 결과가 부족할 때 본 데이터 train 장면 일부 추가 |
| 사용 카메라 | CAM_BACK, CAM_BACK_LEFT, CAM_BACK_RIGHT |
| 제외 장면 | 야간: 장면 설명(description)이 `Night`로 시작하는 장면. 우천: 장면 설명과 사진을 눈으로 확인해 비가 오는 중인 장면만 제외 |

- **왜:** PoC 범위가 주간, 비가 오지 않는 날씨이고(조사 보고서 4장), Drive 15GB 제약이 있다(이슈 7). 후방 좌·우 카메라는 차량이 옆으로 추월하는 순간의 모습을 담고 있어, 근접 추월 상황 학습에 도움이 된다.
- **우천을 단어로만 거르지 않는 이유:** `rain` 단어로 거르면 "after rain"(비가 그친 뒤)처럼 실제로는 비가 오지 않는 장면까지 빠진다(nuScenes 체크리스트 2번).
- **mini에서 야간을 빼면:** 야간 장면 3개(scene-1077, 1094, 1100)가 모두 mini_train에 있어 학습 장면이 8개 → 5개로 줄고, Holland Village 지역이 통째로 빠진다.
- **본 데이터 저장:** 본 데이터는 Drive 15GB에 모두 담을 수 없으므로, 필요한 장면의 후방 카메라 3대 사진과 메타데이터만 골라 저장한다. 다운로드 용량은 받기 전에 확인한다.
- **쉽게:** 교재에서 우리 시험 범위(낮, 맑은 날)에 해당하는 페이지만 골라내는 단계다.

### A2. 키프레임 추출
- 정답 라벨이 달린 키프레임(약 2Hz)만 학습에 사용한다.
- **왜:** 라벨이 없는 프레임은 학습에 쓸 수 없다(이슈 4).

### A3. 클래스 통합
| nuScenes 카테고리 | RearGuard 클래스 |
|---|---|
| vehicle.car, vehicle.emergency.police | 승용차 |
| vehicle.bus.bendy, vehicle.bus.rigid, vehicle.truck, vehicle.trailer, vehicle.construction, vehicle.emergency.ambulance | 대형차 |
| vehicle.motorcycle | 이륜차 |
| vehicle.bicycle, 보행자, 기타 | 제외 |

- **주차 차량도 라벨에서 지우지 않는다.** 검출 모델은 "차가 있는 곳"을 모두 찾는 역할만 하고, "움직이는 차인지"는 이후 추적 단계에서 속도로 판단한다.
- **왜:** 데이터셋의 분류 체계를 제품의 분류 체계에 맞춰야 한다(이슈 5). 주차 차량을 라벨에서 빼면 모델이 "주차된 차는 차가 아니다"라고 잘못 배운다.
- **생각해볼 점: 자전거 제외의 영향.** 같은 원리로, 자전거 라벨을 지우면 모델은 "자전거처럼 생긴 것은 검출 대상이 아니다"라고 배운다. 자전거와 오토바이는 생김새가 비슷하므로, 이 학습이 **오토바이 검출 성능을 떨어뜨릴 수 있다.**
  - **확인 시점:** 이륜차 검출 성능이 낮게 나오면 원인 후보로 먼저 확인한다.
  - **대안:** 자전거를 별도 클래스로 학습시키고, 위험 경고 단계에서만 무시한다.

### A4. 3D 박스 → 2D 박스 변환
- 3D 박스의 꼭짓점 8개를 카메라 파라미터로 이미지에 투영하고, 가장 바깥 좌표로 2D 박스를 만든다.
- 이미지 밖으로 나간 부분은 이미지 경계에서 잘라낸다(클리핑).
- nuScenes 개발 도구(nuscenes-devkit)에 2D 박스 변환 스크립트(`python-sdk/nuscenes/scripts/export_2d_annotations_as_json.py`)가 제공되므로 이를 우선 활용한다. 단, 이 스크립트는 핵심 코드가 아닌 기타 스크립트로 분류되어 있어 결과를 몇 장 그려서 확인한다(nuScenes 체크리스트 6번).
- **왜:** nuScenes 정답은 3D로 되어 있지만, 검출 모델은 2D 박스로 학습한다.
- **쉽게:** 공중에 떠 있는 상자 모양 정답을 사진 위의 네모 정답으로 바꾸는 단계다.

### A5. 박스 필터링
| 조건 | 처리 | 이유 |
|---|---|---|
| 가시성 40% 미만 (nuScenes visibility 등급 최하위) | 제외 | 대부분 가려진 차를 맞히라고 하면 모델이 혼란스러워함 |
| 라이다 점이 0개인 박스 | 제외 | 실제로는 보이지 않는 차일 가능성이 큼 |
| 2D 박스 높이 10픽셀 미만 (원본 기준) | 제외 | 너무 작아 사람도 판별하기 어려움 |
| 카메라로부터 50m 초과 | 제외 | 검출 목표가 30m 이내이며, 먼 차량은 노이즈가 됨 |

- **가시성 등급 주의:** nuScenes의 가시성은 후방 카메라 한 대가 아니라 **카메라 6대 이미지 전체에서 보이는 비율**이다(nuScenes 체크리스트 7번). 후방 카메라에서 실제로 가려진 정도와 다를 수 있으므로, 걸러진 박스 몇 장을 그려서 확인한다.
- **순서 주의:** A4(변환·클리핑) 뒤에 해야 한다. 클리핑 전에는 박스 크기가 실제 보이는 크기와 다르기 때문이다.
- **생각해볼 점: 걸러낸 박스의 영향.** 박스를 라벨에서 빼도 사진 속 차는 그대로 남아 있으므로, 모델은 그 자리를 "차 아님"으로 배운다.
  - 50m 초과 차량을 "차 아님"으로 배우는 것은 검출 목표(30m 이내)와 맞으므로 괜찮을 수 있다.
  - 그러나 많이 가려진 차(가시성 40% 미만)를 "차 아님"으로 배우면, 실전에서 다른 차에 가려진 차를 놓칠 수 있다.
  - **대안 1 - 무시 영역 처리:** 걸러낸 박스를 지우지 않고 "무시 영역"으로 표시한다. 모델은 그 자리에서 맞혀도 틀려도 보상이나 벌점을 받지 않는다. 학습 도구가 이 기능을 지원하는지 확인이 필요하다.
  - **대안 2 - 영향 측정:** 지원되지 않으면 필터링한 버전과 하지 않은 버전을 모두 학습하고, 가려진 차의 검출 성능을 비교한다.

### A6. 장면 단위 데이터 분할
- nuScenes 공식 train/val 분할을 따른다. **프레임 단위로 무작위 분할하지 않는다.**
  - mini: mini_train 8개 장면 / mini_val 2개 장면(scene-0103, scene-0916)
  - 본 데이터: train 700 / val 150 장면 중 필요한 만큼 사용
- **왜:** 같은 장면의 앞뒤 프레임은 거의 똑같은 사진이다. 이것이 학습용과 시험용에 나뉘어 들어가면, 모델이 문제를 "푼" 게 아니라 "외운" 것인데도 점수가 높게 나온다(데이터 누수).
- **순서 주의:** 반드시 A8(증강)보다 먼저 한다. 증강된 사진이 시험용에 섞이는 것도 같은 누수 문제다.

### A7. 리사이즈·레터박스
| 항목 | 설정 |
|---|---|
| 모델 입력 크기 | 416×416 (YOLO26n, CPU 실시간성 고려). 640과 비교 실험(모델 설계 보고서 E3) 후 확정 |
| 방식 | 비율을 유지한 채 축소하고, 남는 부분은 회색으로 채움(레터박스) |

- **왜:** 원본(약 1600×900)을 정사각형으로 억지로 늘리면 차가 찌그러져 보인다. 레터박스는 모양을 유지한다.
- **중요:** 이 설정은 트랙 B4와 **완전히 같아야** 한다.

### A8. 데이터 증강 (학습할 때만 적용)
증강은 원본 사진을 조금씩 바꿔 "다양한 상황을 본 것처럼" 학습시키는 방법이다. 시험용(val)에는 적용하지 않는다.

| 대응 이슈 | 증강 기법 | 초기 설정값 |
|---|---|---|
| 도로 방향 차이 | 좌우 반전 | 확률 50% |
| 시점 차이 (이슈 1) | 무작위 확대·축소, 상하 이동, 약한 원근 변형 | 크기 ±20%, 이동 ±10%, 원근 강도 0.05 |
| 흔들림 부재 (이슈 2) | 모션 블러, 소폭 회전 | 블러 커널 3~9, 확률 30% / 회전 ±5° |
| 역광·그림자 | 밝기·대비 변화, 감마 변화, 그림자 합성 | 밝기·대비 ±25%, 감마 80~120, 그림자 확률 20% |
| 스마트폰 영상 화질 | JPEG 압축 노이즈 | 품질 60~95 |

- **좌우 반전이 특히 중요한 이유:** nuScenes는 미국 보스턴(우측 통행)과 싱가포르(좌측 통행)에서 수집되었다. 한국은 우측 통행이라 차가 자전거의 왼쪽으로 추월한다. 좌우 반전으로 두 방향을 모두 학습시킨다.
- **시점 차이에 대한 한계:** 증강은 카메라 높이 차이(1.5m 이상 vs 0.7m)를 일부만 흉내 낼 수 있다. 실제 효과는 트랙 E 테스트셋으로 확인한다.
- **클래스 불균형:** 이륜차는 승용차보다 훨씬 적을 것으로 예상된다. 학습 전에 클래스별 박스 수를 세고, 이륜차가 전체의 5% 미만이면 이륜차가 포함된 이미지를 2~3배 더 자주 뽑는다(오버샘플링).
- **구현 방법:** 좌우 반전, 확대·축소, 이동, 원근, 회전, 밝기는 YOLO 학습 도구의 내장 인자로 적용한다. 내장 인자가 없는 모션 블러, JPEG 노이즈, 그림자는 장면 분할(A6)이 끝난 뒤 train 사진에만 Albumentations로 변형본을 만들어 추가한다(모델 설계 보고서 §3.2).
- **단위 주의:** 위 표의 원근 강도 0.05는 Albumentations 기준이다. YOLO의 `perspective` 인자는 단위가 달라 0.0001~0.001 범위에서 눈으로 확인한 뒤 정한다.
- **도구:** YOLO 내장 증강, Albumentations (박스 좌표도 함께 자동 변환해 줌)

## 3. 트랙 B: 실시간 추론 전처리

목표: 프레임 입력부터 LED 점등까지 200ms 이하. 따라서 **가볍고 꼭 필요한 처리만** 넣는다.

### B1. 프레임 수신·시간 기록
- OpenCV로 영상 파일을 한 프레임씩 읽고, 각 프레임의 시각(프레임 번호 ÷ FPS)을 함께 기록한다.
- **왜:** 속도와 TTC는 "거리 변화 ÷ 시간"이므로, 정확한 시간 정보가 없으면 계산할 수 없다.
- **생각해볼 점: 가변 프레임레이트 (보완 후보).** "프레임 번호 ÷ FPS"는 프레임이 정확히 일정한 간격으로 찍혔다고 가정한다. 그러나 스마트폰으로 직접 찍은 영상을 입력으로 쓰게 되면, 상황에 따라 프레임 간격이 달라지는 가변 프레임레이트로 저장되어 있을 수 있다.
  - **대안:** OpenCV가 제공하는 프레임별 재생 위치(밀리초, `CAP_PROP_POS_MSEC`)를 시각으로 사용한다.
  - **확인 필요:** 이 값이 실제 프레임 시각을 반영하는지는 OpenCV 백엔드에 따라 다를 수 있으므로, 테스트 영상에서 프레임 간격이 일정하지 않게 나오는지 확인한다.

### B2. 품질 검사 (가벼운 검사만)
| 검사 | 방법 | 기준 (초기값) |
|---|---|---|
| 노출 이상 | 프레임 평균 밝기 | 20 미만 또는 235 초과 (0~255 기준) |
| 심한 흐림 | 라플라시안 분산 (선명도 수치) | 전체 데이터 분포를 본 뒤 하위 5%로 설정 |

- 기준에 걸리면 프레임을 버리지 않고 "신뢰도 낮음" 표시만 붙인다. 연속으로 걸리면 사용자에게 "카메라 상태 확인" 안내를 띄운다.
- **왜:** 역광, 렌즈 먼지(조사 보고서 4장)로 AI가 아무것도 못 보는 상황인데 "안전"이라고 표시하면 위험하다.

### B3. 관심 영역 처리
- 화면 하단의 뒷바퀴·마운트 영역은 검게 가린다(마스킹). 위치는 카메라 장착 후 1회 지정한다.
- 화면 상단의 하늘 부분은 잘라낸다(크롭). 단, 먼 차량이 지평선 근처에 보이므로 지평선 위로 여유를 둔다.
- **왜:** 가림 영역에서 생기는 오검출을 막고, 불필요한 영역을 줄여 연산을 아낀다.
- **순서 주의:** 반드시 B4(리사이즈)보다 먼저 한다. 먼저 줄이고 자르면 먼 차량이 너무 작아진다.
- **학습과의 일관성:** 크롭 비율이 크면 학습 데이터(트랙 A)에도 같은 크롭을 적용해야 한다. PoC에서는 마스킹 위주로 하고 크롭은 최소화한다.

### B4. 리사이즈·레터박스 / B5. 색상 변환·정규화
- B4: 트랙 A7과 동일 (기본 416×416, 레터박스)
- B5: OpenCV의 BGR 순서를 RGB로 바꾸고, 학습 때와 동일한 방식으로 값 범위를 맞춘다.
- **왜:** 학습 때와 다른 방식으로 사진을 넣으면, 같은 장면이라도 AI에게는 다른 사진으로 보인다. 성능이 이유 없이 떨어지는 가장 흔한 원인이다.

### B6. 처리 주기 조절
- 처리 속도 목표 15FPS는 **영상 입력부터 위험도 판단까지 파이프라인 전체 출력** 기준이다(PRD 6.2).
- CPU에서 15FPS를 못 맞추면 2프레임에 1번만 검출하고, 사이 프레임은 추적 필터(칼만 필터)의 예측값으로 채운다. 이때 검출은 초당 7.5회여도 결과는 15FPS로 나온다.

### 실시간 단계에 넣지 않는 전처리
| 전처리 | 넣지 않는 이유 | 대신 하는 것 |
|---|---|---|
| 영상 흔들림 보정 | 연산이 무거워 지연 증가 | 학습 시 모션 블러·회전 증강, 추적 필터로 위치 흔들림 완화 |
| 노이즈 제거 필터 | 주간·맑은 날 범위에서 효과 작음, 지연 증가 | JPEG 노이즈 증강 |
| 명암 보정(CLAHE) | 프레임마다 밝기 처리가 달라져 학습과 불일치 | 밝기·대비·그림자 증강 |
| 전체 이미지 왜곡 보정 | 모든 픽셀을 다시 계산해야 해 무거움 | 트랙 C2에서 필요한 점 몇 개만 보정 |

**쉽게 말하면:** 실전에서는 시간이 없으니, 다양한 상황 대비는 공부할 때(학습 증강) 미리 해두고 실전에서는 최소한의 정리만 한다.

## 4. 트랙 C: 거리 추정 기하 전처리

### C0. 카메라 파라미터 준비 (사전 1회)
| 데이터 | 내부 파라미터 (초점거리 등) | 외부 파라미터 (높이·각도) |
|---|---|---|
| nuScenes | 데이터셋 제공값 | 데이터셋 제공값 |
| 자전거 높이 테스트셋 (iPhone 촬영) | 체커보드 촬영 후 OpenCV 캘리브레이션 | 높이: 줄자 실측 / 각도: 삼각대 설정값 |

### C0.5. 레터박스 좌표 되돌리기
- 모델이 낸 박스는 416×416 레터박스 이미지 기준 좌표다. 그러나 카메라 파라미터(C0)는 원본 이미지 기준이므로, 거리 계산 전에 박스 좌표를 원본 기준으로 되돌린다.
- 원본 1600×900 기준 계산:
  - 축소 비율 = 416 ÷ 1600 = 0.26 → 축소 후 높이 = 900 × 0.26 = 234
  - 위아래 회색 여백 = (416 − 234) ÷ 2 = 91
  - **원래 x = 새 x ÷ 0.26**
  - **원래 y = (새 y − 91) ÷ 0.26**
- 비율과 여백은 고정값으로 넣지 말고, B4에서 레터박스를 만들 때 쓴 값을 그대로 받아 사용한다.
- B3에서 크롭을 했다면, 되돌린 좌표에 잘라낸 만큼(위쪽 크롭 픽셀 수)을 더해야 원본 좌표가 된다.
- **왜:** 이 단계를 빠뜨리면 축소·이동된 좌표로 거리를 계산하게 되어 거리 값이 완전히 틀린다.
- **순서 주의:** 반드시 C1보다 먼저 한다.

### C1. 접지점 추출
- 2D 박스의 **아래쪽 가운데 점**을 차량이 땅에 닿는 점(접지점)으로 사용한다.
- **쉽게:** 사진 속 차가 땅을 밟고 있는 지점을 찾아야, 그 지점이 땅 위에서 얼마나 떨어져 있는지 계산할 수 있다.

### C2. 접지점 왜곡 보정
- 렌즈 왜곡 보정은 이미지 전체가 아니라 접지점 좌표에만 적용한다 (OpenCV undistortPoints).
- **순서 주의:** 반드시 C3보다 먼저 한다. 왜곡된 좌표로 거리를 계산하면 화면 가장자리 차량의 거리가 틀어진다.

### C3. 지면 좌표 변환 (호모그래피)
- 카메라 파라미터와 "도로는 평평하다"는 가정으로 접지점을 실제 도로 위 좌표로 바꾼다.
- 좌표계 정의 (자전거 기준): **x = 뒤쪽 거리(m), y = 옆 간격(m, 왼쪽이 +)**
- **한계:** 경사로·굴곡로에서는 가정이 깨져 오차가 커진다 (조사 보고서 4장, PoC 범위 밖으로 명시).

### C4. 차폭 보정
| 클래스 | 기준 차폭 (초기값) |
|---|---|
| 승용차 | 1.8m |
| 대형차 | 2.5m |
| 이륜차 | 0.8m |

- 박스의 가로 폭과 기준 차폭으로 거리를 한 번 더 계산해, C3 결과와 크게 다르면(30% 이상) 신뢰도를 낮춘다.
- 옆 간격은 차량 중심이 아니라 **자전거에 가까운 쪽 차량 옆면** 기준으로 계산한다: **|y| − 차폭의 절반**. 차가 왼쪽(y가 +)에 있든 오른쪽(y가 −)에 있든 같은 식이 되도록 y의 크기(절댓값)를 쓴다.
- **왜:** 근접 추월의 위험은 차의 옆면이 자전거에 얼마나 가까운가로 결정된다.

### C5. 이상치 제거
| 조건 | 처리 |
|---|---|
| 거리 0m 이하 또는 50m 초과 | 버림 (A5 학습 범위와 같게) |
| 이전 측정 대비 물리적으로 불가능한 이동 (이동 거리 ÷ 경과 시간이 초당 30m, 즉 시속 약 108km 초과. 초기값) | 버림 |

- **이동 기준을 프레임이 아닌 시간으로 정하는 이유:** 데이터마다 프레임 간격이 다르다(nuScenes 카메라 12Hz·키프레임 2Hz, 처리 속도 15FPS). "프레임당 몇 m"로 정하면 데이터마다 기준이 달라지므로, B1에서 기록한 시각으로 속도를 계산해 비교한다.

- 남은 값은 추적 필터(칼만 필터)에 넣어 부드럽게 만든 뒤 속도·TTC·예측 측면 간격을 계산한다.

### C6. 평가용 정답 정리 (nuScenes)
- nuScenes 3D 박스의 위치(`translation`)는 **박스의 3D 중심점**이다. 앞뒤·좌우뿐 아니라 **높이 방향으로도 중심**이다(nuScenes 체크리스트 12번). 그러나 카메라로 추정하는 위치는 **차량 앞면의 바닥**이다.
- 따라서 평가 전에 정답을 두 번 옮긴다.
  1. 차량 중심에서 **카메라 쪽 면**으로 차 길이의 절반만큼 옮긴다 (뒤에서 다가오는 차는 앞면).
  2. 높이를 차 높이의 절반만큼 내려 **바닥**에 맞춘다.
- **왜:** 이걸 하지 않으면 추정이 정확해도 차 길이의 절반(승용차 약 2m)만큼 틀린 것처럼 채점된다.
- **한계:** nuScenes 카메라는 자전거보다 높이 달려 있으므로, 여기서는 "계산 방법이 맞는지"를 검증하고, 자전거 높이에서의 정확도는 트랙 E로 검증한다.

## 5. 트랙 D: 판단 로직 검증용 합성 궤적 데이터

### D1. 시나리오 정의
| 시나리오 | 초기 거리 | 상대 속도 | 추월 시 옆 간격 | 기대 위험도 |
|---|---|---|---|---|
| 안전 추월 | 30~50m | 20~40km/h | 1.5~2.5m (대형차는 2.0~2.5m) | 1단계 |
| 근접 추월 | 30~50m | 20~40km/h | 0.5~1.5m (대형차는 0.5~2.0m) | 2단계 |
| 충돌 경로 | 20~40m | 20~40km/h | 0~0.5m | 3단계 |
| 정지·주차 차량 | 10~30m | 자전거가 멀어짐 | 무관 | 0단계 |

- 차종(승용·대형·이륜)을 섞어 각 시나리오를 생성한다. 시간 간격은 실제 처리 주기와 같게(15FPS) 한다.
- 위험도 기준은 PRD F3 표를 따른다. 대형차는 1단계 기준이 2.0m 이상이므로, 안전 추월 시나리오의 대형차는 옆 간격을 2.0m 이상으로 생성한다.

### D2. 정답 생성
- 노이즈 없는 궤적에서 진짜 TTC와 최근접 통과 거리(CPA)를 계산해 정답 위험도를 기록한다.

### D3. 측정 오차 주입
| 오차 종류 | 설정 (초기값) |
|---|---|
| 위치 흔들림 | 표준편차 0.3m (트랙 C 평가 결과로 갱신) |
| 검출 누락 | 프레임의 5% 무작위 누락 |
| 추적 ID 뒤바뀜 | 시나리오의 2%에서 1회 발생 |

- **왜:** 실제 판단 로직은 "눈"이 넘겨주는 약간 틀린 숫자를 받는다. 완벽한 숫자로만 시험하면 실전에서 깜빡임이나 오경보가 나는 것을 미리 알 수 없다.
- **쉽게:** 시력이 약간 안 좋은 상태에서도 판단을 잘하는지 시험하는 것이다.

### D4. 균형 조정
- 시나리오별 개수를 같게 맞춘다 (예: 각 200개). 실제 도로처럼 위험 장면이 1%뿐이면 판단 로직이 위험 상황을 잘 잡는지 평가할 수 없다.

### D5. 레이더 모사 규칙 (비교 기준선)
PRD 핵심 지표("레이더 방식 대비 불필요 경고 50% 이상 감소")의 비교 대상이다. D3에서 오차를 주입한 **같은 합성 궤적**에 거리와 접근 속도만 쓰는 규칙을 적용한다.

| 레이더 모사 규칙 (초기값) | 판단 |
|---|---|
| 접근 중이고 거리 < 30m | 경고 (2단계에 해당) |
| 거리 ÷ 접근 속도 < 2.0s | 위험 (3단계에 해당) |

- 옆 간격과 차종은 사용하지 않는다. 레이더는 이 정보를 알 수 없기 때문이다.
- **채점 기준 (PRD 6.1):**
  - 불필요 경고: 정답이 0·1단계(안전)인 장면에서 2단계 이상 경고가 울린 경우
  - 위험 추월 감지율: 정답이 2·3단계인 장면 중 2단계 이상으로 판단한 비율
- RearGuard 규칙과 레이더 모사 규칙의 불필요 경고 수를 비교해 50% 이상 줄었는지, 이때 감지율 90% 이상을 유지하는지 확인한다.
- **쉽게:** 같은 시험지를 "거리만 보는 학생"과 "옆 간격까지 보는 학생"에게 풀게 하고, 괜히 소리친 횟수를 비교하는 것이다.

## 6. 트랙 E: 자전거 높이 테스트셋 (iPhone)

### E1. 촬영
| 항목 | 설정 |
|---|---|
| 장비 | iPhone 일반 렌즈(촬영 도구로만 사용), 삼각대 |
| 카메라 각도 | 약간 아래(약 5°) |
| 대상 | 주차된 차량 (승용차 위주, 가능하면 대형차·이륜차 포함) |
| 기본 세트 (70cm) | 뒤쪽 거리 5·10·15·20·25·30m × 옆 간격 0.5·1.0·1.5·2.0·2.5m = 30장 |
| 높이 변경 세트 (60·80cm) | 뒤쪽 거리 10·20·30m × 옆 간격 0.5·1.5m = 높이별 6장, 총 12장 |
| 조건 | 주간, 맑음 또는 흐림 |

- 차가 아닌 카메라를 옮기며 찍으므로 운전자가 필요 없다.
- **옆 간격의 기준:** 카메라 바로 뒤로 그은 직선에서 **카메라 쪽 차량 옆면**까지의 거리 (C4와 같은 기준).
- **옆 간격을 0.5~2.5m로 잡은 이유:** PRD의 측면 간격 오차 목표가 0.5~2.5m 구간 기준이다.
- **높이 변경 세트를 찍는 이유:** PRD F4 지표("장착 높이 변경 후 측면 간격 오차 증가 ≤ 0.1m")를 측정하기 위해서다. 70cm 기본 세트와 **같은 위치**에서 찍어야 비교할 수 있다. 차는 그대로 두고 삼각대 높이만 바꿔 이어서 찍으면 된다.

### E2. 정답 기록
- 촬영마다 표에 기록한다: 파일명 / 뒤쪽 거리 / 옆 간격 / 차종 / 날씨·조명
- 거리 기준점은 트랙 C6과 같게 **차량 앞면 바닥**으로 잰다.

### E3. 비식별화
- 번호판과 사람 얼굴을 흐리게 처리한 뒤 저장·공개한다 (조사 보고서 이슈 6).

### E4. 라벨링
- 42장(기본 30장 + 높이 변경 12장)에 차량 2D 박스를 그린다. 도구: Label Studio 또는 CVAT (예상 소요 1~2시간).

### E5. 사용 규칙
- 트랙 B·C와 **완전히 같은 전처리**를 거쳐 평가한다. 거리 계산에는 사진마다 실제 촬영 높이(60·70·80cm)를 입력한다.
- **F4 평가:** 60·80cm 사진의 측면 간격 오차를 70cm 같은 위치 사진의 오차와 비교한다. 증가량이 0.1m 이하이면 목표 달성이다.
- **학습에는 절대 사용하지 않는다.** 시험지를 미리 보고 공부하면 점수가 의미 없어진다.

## 10. 초보자를 위한 핵심 정리

- **전처리는 세 번 나온다.** 공부 전(교재 정리, 트랙 A), 실전 중(화면 다듬기, 트랙 B), 계산 전(거리 계산 준비, 트랙 C).
- **공부할 때와 실전에서 사진을 다루는 방식은 같아야 한다.** 크기를 줄이는 방법이나 색 순서가 다르면 AI는 같은 장면도 처음 보는 사진처럼 느낀다.
- **시험지는 미리 보면 안 된다.** 비슷한 사진이 학습과 시험에 섞이거나(데이터 누수), 테스트셋을 학습에 쓰면 점수가 실제 실력보다 높게 나온다.
- **실전은 시간이 없다.** 다양한 상황 대비는 공부할 때 증강으로 미리 하고, 실전 전처리는 최소한으로 한다.
- **정답과 추정은 같은 기준점으로 비교한다.** 차량 중심과 차량 앞면처럼 기준이 다르면 정확해도 틀린 것처럼 보인다.
